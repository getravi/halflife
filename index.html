Phase 00 · Weeks 1–8

Programming
foundations

This phase assumes you are starting close to zero. You will learn Python properly, then async Python, then array thinking, then the math deep learning is actually made of. Nothing here is optional — every later phase silently assumes all of it, and the two things people most often skip (async concurrency and sampling variance) are exactly the two that block Phase 2. Eight weeks at 25 hours is about 200 hours. Spend them on your own keyboard.

0% complete
No AI-generated code in this phase. An assistant will produce working programs and leave you unable to debug a shape mismatch in Phase 1. Explainer and tutor use is always allowed; a code generator is banned on exit checks and on first attempts. This ban lifts at the end of Phase 0 — from Phase 1 onward, driving a coding agent well is an explicit skill you are graded on, not a shortcut you are avoiding.
Go public in week 1, not week 22. Create the public repo on day one and commit to it every week. Post a short public build log every two weeks — what you built, what broke, what the number was. Twelve months of visible work beats one polished capstone with no history behind it.
Check the structured-program calendars in week 1. ARENA, MATS and the Anthropic Fellows programme run on fixed application windows, and the windows do not wait for you to feel ready. Put every deadline inside the next 52 weeks in your calendar now, and apply to all of them — including the ones you think you will fail.
Task 01 Set your operating rhythm Exercise
Go public on day one
Create the public repo now, before you can write anything worth putting in it. Add a README that says what you are doing and why, and commit something every week you work. The first public artifact in the old version of this plan landed at week 22 — five months of zero external signal, which is the single most common point at which solo learners quietly stop.

Join one community and actually show up
Pick exactly one — EleutherAI, Prime Intellect, or the Inspect/AISI community — and post weekly. Answer questions slightly below your level; that is how you become known, and being known is the bottleneck this plan cannot teach around. One community you attend beats four you lurk in.

MATS ↗

Task 02 Python from zero Exercise
Set up, go public, write your first programs
Install Python 3.13 and Astral's uv. Create your project with uv init, run scripts, live in the REPL. Learn variables, numbers, strings, f-strings and print debugging, then write 20 tiny programs from a blank file — no tutorial on autopilot, type every line. Create the public GitHub repo today and push week 1's work to it.
Week 1
docs.astral.sh/uv ↗
Data structures and control flow
Lists, dicts, sets, tuples. if/for/while, slicing, iteration, nesting. Learn what mutability means and why it bites — mutate a list inside a function and watch the caller's copy change. Build a word-frequency counter, a to-do list and a text-file parser from an empty file, not from a template.
Week 2
docs.python.org tutorial ↗
Functions, files, errors, and classes
Function arguments and return values, scope, exceptions and try/except, reading and writing files, modules and imports, and basic classes with __init__. Learn to read a traceback from the bottom up and fix the actual line it names instead of guessing. Every program from here on gets a function per step.
Week 3
Exit check: word frequencies from an empty file
From a blank file, write a program that reads a text file, counts word frequencies, sorts by count, and writes the top 20 to a new file — a function per step, with error handling for a missing input file. No copying, no AI assistance. It passes when the output is correct on a file you did not write and it fails cleanly on a path that does not exist.
Week 3
Task 03 Python fluency and async Exercise
The idioms you will actually read
List, dict and set comprehensions, generators and yield, decorators, context managers, *args and **kwargs, and dataclasses. Write each one by hand until you stop reaching for the docs. You are not learning these to write clever code — you are learning them so that other people's ML code stops looking like noise.
Week 3
Type annotations and tooling
Set up ruff and mypy and make both run on save in your editor. Annotate everything you write from here on, including return types. Strong typing and linting habits are what make a large evals codebase reviewable; adding them later is much more work than starting with them.
Week 4
docs.astral.sh/ruff ↗
Async Python: asyncio and TaskGroup
Learn async def, await, the event loop, asyncio.run, gather, and TaskGroup for structured concurrency. Understand precisely why a blocking call inside a coroutine stalls every other task on the loop, and prove it to yourself with time.sleep versus asyncio.sleep. This is the single highest-leverage thing in Phase 0.
Week 4
docs.python.org asyncio ↗
Bounded concurrency, retries and backoff
Write an async client that fans out N requests against a rate-limited endpoint with a Semaphore capping in-flight calls, exponential backoff with jitter on 429s and 5xxs, and a per-request timeout. Make partial failure explicit: return results and errors, never silently drop a task. Every eval harness in Phase 3 is this loop with a scorer bolted on.
Week 4
python-httpx.org async ↗
Exit check: typed LRU cache and a concurrent fetcher
Write a generic, fully typed LRU cache from scratch using only the standard library — no functools.lru_cache. Then write an async fetcher that runs 100 tasks with a concurrency cap of 10 and retries transient failures. Both pass when mypy is clean and your own tests cover eviction order and the retry path.
Week 4
Async is not a nice-to-have. Phase 3 asks you to run thousands of model calls against checkpoints with retries, caching and cost accounting. If asyncio is still uncomfortable then, you will write a threaded mess and spend a week debugging it. Learn it here where the stakes are a toy fetcher.
Task 04 NumPy array thinking Exercise
Think in arrays, not loops
Work the NumPy 100 exercises. Concentrate on broadcasting rules, fancy indexing, axis semantics and einsum. Ban Python for-loops over array elements entirely — if you catch yourself writing one, that is the exercise telling you which concept you skipped.
Week 5
github.com/rougier/numpy-100 ↗
Core ops by hand
Implement matrix multiply, softmax and layer norm from scratch in NumPy. Make softmax numerically stable by subtracting the row max and be able to say what happens if you do not. Verify each against a reference implementation to 1e-6.
Week 5
numpy broadcasting ↗
Exit check: attention in einsum
Implement scaled dot-product attention (Q, K, V to output, with a causal mask) using only np.einsum and np.exp. No loops, no reshape gymnastics you cannot explain. It passes when it matches a PyTorch reference to 1e-5 and you can state what each index letter in your einsum string means.
Week 5
numpy.einsum ↗
Array thinking is non-negotiable. PyTorch and JAX are both high-dimensional array transform languages wearing a neural-network costume. If shapes and axes are not fluent here, every model you touch later becomes a shape-error guessing game.
Task 05 Math refresh Theory
Linear algebra warmup
Eigendecomposition, SVD, matrix rank, projections and change of basis. Work ten problems by hand on paper before touching NumPy, then check each numerically. Low-rank structure is the whole idea behind LoRA in Phase 3, and rank is where it starts.
Week 6
mml-book.github.io ↗
Calculus and backprop by hand
Chain rule in vector form, Jacobians, and why reverse-mode is the cheap direction for scalar losses. Derive backpropagation for a 2-layer MLP on paper, including the shapes of every intermediate. Then implement it in NumPy and verify against a finite-difference gradient check.
Week 6
cs231n backprop notes ↗
Probability, entropy and cross-entropy
Entropy, cross-entropy, KL divergence and perplexity. Derive the softmax-plus-cross-entropy gradient by hand and notice how much it simplifies — that simplification is why every language model trains this way. Be able to convert between a loss in nats and a perplexity without looking it up.
Week 7
Sampling variance and the bootstrap
Learn what a standard error actually is, how it shrinks with n, and how to build a bootstrap confidence interval from resampled data. Simulate it: draw 200 samples from a known distribution, bootstrap the mean, and check the interval covers the truth about 95% of the time. Then do the same for a paired difference between two conditions.
Week 7
scipy.stats.bootstrap ↗
The bootstrap is the single most reused tool in this plan. Every eval number you report from Phase 1 onward — nanochat variance, benchmark scores, judge agreement — needs an interval attached. Learning it now costs a day; not learning it means a year of point estimates nobody can trust.
Task 06 Optimizer math Exercise
Complexity intuition, not interview prep
Read a loop nest and state its time and space complexity without thinking. Cover the handful of patterns you actually meet in ML code: sorting, hashing, sliding windows, and the difference between an O(n²) attention and an O(n) scan. That is all the algorithms content this plan needs.
Week 7
Derive and implement SGD, momentum, Adam and AdamW
Write each update rule on paper first, including the bias correction terms in Adam and why they exist. Then implement all four in NumPy and verify Adam matches torch.optim.Adam step for step on a fixed seed. Finish by explaining what decoupled weight decay in AdamW changes versus L2 added to the loss.
Week 7
arXiv 1412.6980 — Adam ↗
Watch the optimizer misbehave
Take your Adam implementation and break it deliberately: drop the bias correction, set epsilon to zero, set beta2 to 0.9, crank the learning rate. Plot the loss curve for each. Recognising these shapes on sight saves days of debugging in Phase 1 and Phase 2.
Week 7
arXiv 1711.05101 — AdamW ↗
Zero LeetCode. Earlier versions of this plan budgeted five mediums. They are cut — nothing in evals or applied research hiring is gated on them, and the hours buy far more here. The optimizer math is the deliverable, and you will use it in every training loop for the next 44 weeks.
Task 07 Git, Linux and remote boxes Exercise
The git you will actually use
Branch, commit, push, pull, resolve a merge conflict, read a diff, and write a commit message that says why. Learn git bisect properly by running one on a repo with a deliberately planted bug. Skip the exotica — interactive rebase mastery, cherry-pick and worktrees are not what is stopping you.
Week 8
git-scm.com/docs/git-bisect ↗
Linux, ssh and tmux hygiene
You will rent GPU boxes starting in Phase 1, and everything you do on them happens over ssh. Learn key-based auth and ~/.ssh/config aliases, scp and rsync for moving checkpoints, and tmux so a dropped connection does not kill a training run. Practise the whole loop on a cheap CPU instance before there is a GPU bill attached to your mistakes.
Week 8
missing.csail.mit.edu ↗
Workspace and profiling
Set up uv-managed environments, a working VS Code Python setup, and pytest running on your own code. Then learn cProfile: profile a deliberately bottlenecked loop, find the slow call, fix it, and measure the difference. Never optimise anything you have not profiled.
Week 8
docs.python.org profile ↗
Set a billing alert before you rent anything. The most common way this plan goes wrong financially is an instance left running over a weekend. Configure the alert, and make tmux plus an explicit shutdown command part of the muscle memory now, while the box costs cents an hour.

You're ready for Phase 1 when…

  • From an empty file, you can write a correct word-frequency program with a function per step and clean handling of a missing input file
  • You can read a traceback and fix the line it names, without guessing and without pasting it anywhere
  • You can write a generic typed LRU cache from the standard library alone, and mypy is clean on it
  • You can write an async fan-out that caps concurrency, retries transient failures with backoff, and reports partial failure explicitly

Phase 01 · Weeks 9–20

Deep learning
& transformers

Twelve weeks to go from no autograd to a trained chat model you paid for yourself. You build micrograd, then makemore, then the boring PyTorch engineering nobody teaches, then CS336 assignment 1 against a real test suite, then read what changed in architectures since 2023, then run and dissect nanochat. The transformer gets built once, properly, and graded by tests rather than by your own optimism.

Three public artifacts come out of this phase, not one at the end. Micrograd and makemore at week 11, the green CS336 tests at week 17, the nanochat writeup at week 20. Push each as you finish it. Nobody is watching yet, which is exactly why it costs nothing to build the habit now.
Task 01 Karpathy's Zero to Hero Exercise
Build micrograd first
Watch the micrograd lecture and implement scalar-level reverse-mode autograd from scratch: a Value node, a backward closure per operation, and a topological sort for the backward pass. Then train a tiny MLP on a two-class toy dataset with it. Do this before makemore — the whole series assumes you already know what .backward() is doing, and building it first is what makes every later framework bug legible.
Week 9
github.com/karpathy/micrograd ↗
Then makemore, all the way through
Build bigram, MLP, and the deeper character-level models in sequence. The payload is not the models — it is initialisation scale, batch normalisation, and the activation and gradient diagnostics Karpathy plots. Learn to look at a histogram of activations and say which layer is saturating.
Week 10
github.com/karpathy/makemore ↗
Diagnostics you keep
Extract the diagnostic tooling from makemore into your own small module: activation and gradient histograms per layer, update-to-weight ratio, and a loss curve with a moving average. You will reuse this in every training run for the rest of the plan. Push it to the public repo.
Week 11
Neural Networks: Zero to Hero ↗
Exit check: autograd from memory
Close every tab and reimplement scalar autograd from scratch: add, multiply, tanh, and a backward pass that handles a node used twice. It passes when the gradients match a PyTorch reference on a small expression graph, including the reused-node case that catches people who accumulate instead of overwrite.
Week 11
Publish it, week 11
Push micrograd and makemore to the public repo you created in week 1, with a README that says what each one is and links the notebook where the gradients check out numerically. Write one short post about the bug that cost you the most time. This is your first technical artifact and its job is to exist, not to impress — but it is also the thing that makes weeks 9 to 11 visible to anyone who looks.
Week 11
Type the code, do not paste it. This is the one place where copying costs the most, because backprop intuition is the thing you are actually buying. Watch, pause, write it yourself, and let it break. The series has had no new lectures since Aug 2024 and none are coming — but micrograd and makemore remain the best on-ramp that exists.
Task 02 PyTorch engineering Exercise
Input pipelines that do not starve the GPU
Learn Dataset, DataLoader, num_workers, pin_memory, collate_fn and why a slow collate silently caps your throughput. Instrument a training step to measure data-wait time versus compute time. If the GPU is idle a third of the time, you have a data bug, not a model bug.
Week 12
pytorch.org DataLoader ↗
Mixed precision and gradient accumulation
Run a training loop in bf16 and in fp16 with a GradScaler, and know why bf16 usually needs no scaler while fp16 does. Then implement gradient accumulation to reach an effective batch size your card cannot hold, and confirm the loss curve matches the equivalent large-batch run. Get the accumulation-versus-scheduler-step interaction right — stepping the scheduler per micro-batch is a classic silent bug.
Week 12
pytorch.org AMP examples ↗
Checkpoint, resume, and survive OOM
Save and restore model, optimizer, scheduler, scaler and RNG state, then prove it: kill a run mid-epoch, resume, and show the loss curve is continuous across the seam. Separately, reproduce a CUDA OOM on purpose and work through the standard fixes — smaller micro-batch, activation checkpointing, freeing stale references, and reading the allocator summary.
Week 12
pytorch.org saving & loading ↗
Numerical debugging
Learn the standard first moves when a loss goes NaN: check for inf in the inputs, look for a division by a near-zero norm, verify the softmax is max-subtracted, and clip the gradient norm. Practise gradcheck on a custom autograd function. Build the habit of overfitting a single batch to zero loss before ever launching a real run — if it cannot memorise 8 examples, the bug is in your code, not your hyperparameters.
Week 13
karpathy.github.io recipe ↗
Experiment tracking and reproducibility
Wire up a tracker — Weights & Biases or an equivalent — and log config, git SHA, loss curves, learning rate, grad norm and throughput for every run. Seed everything and read what PyTorch does and does not guarantee about determinism. A run you cannot reproduce or point at is not a result, and you will need this discipline for the benchmark audit in Phase 3.
Week 13
docs.wandb.ai ↗
This task is the one nobody teaches and everybody needs. Tutorials end at loss.backward(); jobs start there. Checkpoint/resume, OOM triage and honest experiment logs are what separates someone who has run a training job from someone who has watched one.
Task 03 Stanford CS336 · assignment 1 Exercise
Watch the lectures before touching the code
CS336 'Language Modeling from Scratch' is the best structured treatment of this material and the course materials are public — lectures, slides and assignments. Watch the first five lectures and take notes by hand before you open the assignment. The paid Stanford Online certificate track is a separate product you do not need.

stanford-cs336.github.io ↗
BPE tokenizer, green
Implement byte-level BPE training and encoding against the course test suite. Get the special-token handling and the pre-tokenization regex right; that is where most of the failures live. Then train it on the assignment's corpus and inspect the merges — you should be able to explain why the vocabulary looks the way it does.
Week 14
cs336 assignment1-basics ↗
Transformer, green
Build the model end to end: RMSNorm, RoPE, multi-head self-attention with causal masking, SwiGLU feed-forward, and the residual structure that ties them together. Run the provided tests until every transformer test passes. This is the one from-scratch transformer in the entire plan — earlier drafts built it four times, which was three times too many.
Week 15
arXiv 1910.07467 — RMSNorm ↗
Optimizer, training loop, and a real run
Implement AdamW, cosine schedule with warmup, and gradient clipping against the tests, then train the model on TinyStories or OpenWebText and log the loss curve. Aim to get a sample of generated text that is recognisably English. Record wall-clock time, hardware and cost alongside the loss.
Week 16

You pass this task when the tokenizer tests and the transformer tests are green — those two are mandatory and non-negotiable. The optimizer and training-loop tests are optional: if they are still red at the end of week 17, write down exactly which assertions fail and what you think is wrong, commit that note, and move on. Week 17
Publish the green tests, week 17
Push the assignment work public with the test output in the README, including whatever you left as partial credit and a sentence on why. A passing course test suite is the only externally graded evidence in the entire 52 weeks — it is worth more than three self-assessed projects, and it is worth linking directly rather than burying in a repo tree.
Week 17
Four weeks, and partial credit is the plan. Earlier versions budgeted two weeks for this and were wrong by roughly 2.5×. A public test suite that fails loudly is worth more than a tutorial you believe you understood — but a green tokenizer and a green transformer already carry the portfolio value. Shipping partial with an honest note beats stalling the phase.
Task 04 What changed since 2023 Theory
Attention, and the three fixes that stuck
Read 'Attention Is All You Need' properly — you should be able to diagram every component from memory. Then read the three modifications that are now universal: FlashAttention for why attention is memory-bandwidth-bound rather than compute-bound, RoPE for why learned positional embeddings were replaced, and GQA for how the KV cache shrinks. Trace KV-cache mechanics by hand: what gets stored, at which layer, and when it invalidates.
Week 18
arXiv 1706.03762 ↗
FlashAttention and the memory hierarchy
Read FlashAttention-2 for the tiling and work-partitioning argument, and understand why never materialising the N×N attention matrix is the whole trick. Be able to state, roughly, the arithmetic intensity of an attention layer and why that number decides whether you are compute-bound or bandwidth-bound. This is the direct on-ramp to the Triton work in Phase 2.
Week 18
arXiv 2307.08691 — FlashAttention-2 ↗
Mixture of experts and load balancing
Read Switch Transformer for top-k routing, the auxiliary load-balancing loss and capacity factors, then Mixtral for what a shipped sparse model actually looks like. The question to hold onto is why routing collapse happens and what the balancing loss is really buying. Sparse models are now the default at frontier scale, so this is not optional background.
Week 18
arXiv 2101.03961 — Switch Transformer ↗
MLA and long context
Read the DeepSeek-V2 paper for multi-head latent attention — compressing the KV cache into a low-rank latent instead of sharing heads — and compare its tradeoff against GQA. Then read YaRN for how context windows get extended past the training length. Both are about the same underlying constraint: the KV cache is what makes long-context inference expensive.
Week 18
arXiv 2405.04434 — DeepSeek-V2 ↗
Hybrid and linear attention
Read Mamba for selective state-space models and the linear-attention framing that preceded it. Understand what a fixed-size recurrent state buys you at inference and what it costs you in recall. Most 2026 production models are hybrids rather than pure attention or pure SSM, so know why the mix exists rather than which one 'won'.
Week 18
arXiv 2312.00752 — Mamba ↗
Quantization for people who run evals
Read GPTQ and AWQ for post-training weight quantization, and learn the practical vocabulary: int8 versus int4, per-channel versus per-group scales, weight-only versus activation quantization, and KV-cache quantization. The reason this matters to you is evals: a quantized checkpoint is a different model, and comparing an int4 serve against an fp16 baseline without saying so is a reproducibility failure you will meet in Phase 3.
Week 18
arXiv 2210.17323 — GPTQ ↗
This week is reading, and that is deliberate. Do not try to implement MoE routing or an SSM here — you would spend three weeks and learn less. The deliverable is a short public post explaining each of these six in your own words, with the tradeoff each one makes. If you cannot write the tradeoff down, you have not read it yet.
Task 05 nanochat: the full pipeline Exercise
Run the speedrun first
Rent the box and execute the speedrun end to end before reading a single file. You will not understand most of it, and that is the point — you now have a working chat model, a wall-clock number, a bill, and a set of logs to explain. Reading a codebase you have already run is a completely different experience from reading one you have not.
Week 19
github.com/karpathy/nanochat ↗
Then read the whole repo
Now read every file: tokenization, pretraining, midtraining, SFT, RL, eval, and inference with the web UI. It is the one readable codebase that covers the entire stack, and a single --depth knob sets most of the hyperparameters. For each stage, find the line in the log you produced last week that corresponds to it.
Week 19
Change one thing and measure it
Pick a single variable — depth, learning rate schedule, data mixture, or the SFT set — change only that, rerun, and write down what moved and by how much. Then rerun the baseline with a different seed so you can say whether your effect is larger than run-to-run noise. Report the number with a bootstrap interval, not as a point estimate.
Week 20
Write it up honestly
Publish a writeup with real costs, real wall-clock times, the hardware you used, the eval numbers, and the variance. Include what went wrong and what you would spend differently. This is the second half of flagship deliverable three, alongside the green CS336 assignment, and honest numbers are what make it credible.
Week 20
Budget $150–400, not $48. The README's headline figure covers one clean speedrun on 8×H100 at on-demand pricing. Your real spend includes a failed launch, a config you got wrong, the baseline rerun for variance, and the ablation. Set a hard cap, set a billing alert, use spot where you can, and never leave an instance running overnight.

Phase 02 · Weeks 21–38

Evals &
environments

Task 01 Stand up a served endpoint Exercise
Stand up vLLM
Serve a small open model with `vllm serve` and hit it through the OpenAI-compatible endpoint. Get comfortable with the knobs that actually matter: `--max-model-len`, `--gpu-memory-utilization`, `--max-num-seqs`, and the engine's startup log where it reports how many KV cache blocks it allocated. Everything else in this task is a variation on this server.
Week 21
vLLM docs ↗
Continuous batching and paged KV cache
Static batching wastes the GPU whenever sequences in a batch finish at different times; continuous batching admits new requests at every decode step instead. PagedAttention stores the KV cache in fixed-size blocks with an indirection table, which is what makes that admission cheap and eliminates the fragmentation of contiguous per-sequence allocation. Read how blocks are allocated, shared and evicted — preemption under memory pressure is a real behaviour you will have to explain when throughput collapses.
Week 21
vLLM — paged attention ↗
Read the PagedAttention paper
The original vLLM paper is short and states the problem cleanly: KV cache memory, not compute, is what bounds serving throughput for LLMs, and pre-allocating contiguous cache for the maximum sequence length wastes most of it. Read it for the framing and the memory accounting, which carry over to every serving system that came after.
Week 21
arXiv 2309.06180 — PagedAttention ↗
Prefix caching
Automatic prefix caching hashes KV blocks so requests sharing a prefix reuse them instead of recomputing. This is the single largest win available to eval and RL workloads, where hundreds of samples share one long system prompt and few-shot block. Measure it: run the same eval batch with prefix caching on and off and record time-to-first-token and total throughput. That measured delta is a number worth putting in a writeup.
Week 22
vLLM — automatic prefix caching ↗
Throughput versus latency, measured
Build a small load generator and sweep concurrency, recording time-to-first-token, inter-token latency and total output tokens/second at each level. You will see the shape everyone talks about: throughput rises with concurrency until the KV cache saturates, while per-request latency degrades from the first request onward. Know where your endpoint's knee is, because Phase 3 eval runs will sit right on it.
Week 22
Wire the endpoint to an RL and eval harness
Close the loop that motivates this whole task. Prime Intellect's `verifiers` library assumes an OpenAI-compatible endpoint backed by vLLM, so point it at the server you just built and run a trivial rollout. You are not learning the library yet — that comes in week 25 — you are proving the plumbing works and seeing where the endpoint becomes the bottleneck in a rollout loop.
Week 22
github.com/willccbb/verifiers ↗
This is the task that makes Phase 3 possible. Every eval you write and every RL rollout you generate goes through a served endpoint. When an eval run is inexplicably slow, when throughput collapses at sample 400, when two runs of the same eval disagree — the cause is usually the serving layer, not your harness. Task 02 Write your own agent harness Agent
The loop, from a blank file
No framework. Write the while loop yourself: send messages, parse the tool call out of the response, dispatch to a Python function, append the result as a tool-result message, repeat until the model stops or you hit a limit. Two hundred lines gets you a working agent, and afterwards every agent framework reads as a config file rather than magic.
Week 23
Building effective agents ↗
Tool schema design is the actual skill
Write five tools and then rewrite them. Names and descriptions are prompt, not documentation; the model fails on ambiguous parameters far more than on hard reasoning. Return errors as content the model can act on rather than as exceptions, and keep tool outputs small enough that ten calls do not blow the context.
Week 23
Writing tools for agents ↗
Multi-turn state, error recovery, hard limits
Add the things that keep a harness alive over 50 turns: bounded concurrency with the asyncio patterns from Phase 0, retries with backoff on transient API errors, a step limit, a wall-clock limit, and a cost cap that aborts the run. Then deliberately break a tool and watch whether your agent loops forever — most first drafts do.
Week 23
Context compaction
Long agentic runs die from context, not capability. Implement one strategy and measure it: summarise older turns, drop stale tool outputs while keeping their identifiers, or offload results to files the agent can re-read. Compare task success with and without compaction on the same tasks so you have a number, not a preference.
Week 24
Effective context engineering ↗
Speak MCP
Wrap two of your tools as an MCP server and connect your harness to it as a client. Read enough of the spec to know what a tool, a resource, and a prompt are, and how transport and capability negotiation work. Interview-relevant and directly relevant to shipping an environment other people's harnesses can call.
Week 24
MCP introduction ↗
This harness is a tool you will use for the rest of the plan. The benchmark audit in weeks 45–46 needs a scaffold you fully control, and the environment in week 48 needs a client you can point at it. Build it well now and you stop paying for it later.
Put the cost cap in on day one. An agent loop that retries a failing tool call can burn a hundred dollars overnight without producing a single completed task. Cap tokens per run and total spend per experiment before you leave anything unattended.

Task 04 Statistics & experimental design Theory
Decide the sample size before you run anything
Work through power analysis for the comparisons you actually make: two models on one benchmark, one model before and after a change. Compute the minimum detectable effect for n = 100, 500, 2000 questions and see how brutal the small-n case is. The reflex you want is refusing to run an eval until you know what difference it could even detect.
Week 27
statsmodels power ↗
Read the error-bars paper and apply it the same day
Read Anthropic's "Adding Error Bars to Evals" end to end. It gives you the standard error for a mean over questions, the clustered case when questions come in groups, and the paired analysis that makes model comparisons far tighter. Then recompute error bars on a real eval result you already have.
Week 27
arXiv 2411.00640 ↗
Paired comparison and variance decomposition
Two models scored on the same questions are paired data — analysing them as independent samples throws away most of your power. Implement the paired difference test, then decompose total variance into question difficulty, sampling temperature, and seed. Report which source dominates; usually it is question variance and that changes what you should buy more of.
Week 27
scipy.stats.bootstrap ↗
Multiple comparisons and effect sizes
Once you run twelve ablations against one baseline, one of them is significant by accident. Implement Benjamini–Hochberg and Bonferroni corrections and see what survives. Then stop reporting p-values as the headline: report the effect size with a bootstrap confidence interval, because a real but tiny difference and a large uncertain one are different findings.
Week 28
statsmodels multipletests ↗
Exit check: redo an old result honestly
Take the single-variable change you measured in the nanochat week and redo the analysis: paired where possible, bootstrap CI, stated n, stated seeds. Write one paragraph saying whether the difference you reported survives. If it does not, say so publicly — that paragraph is worth more in an interview than the original result.
Week 28
A statistical approach to model evals ↗
Apply it to your own numbers
Take the baseline table you published in week 26 and redo it properly: compute the sample size you actually needed, add bootstrap intervals, and use paired comparison where models saw the same tasks. Commit the corrected table with a note saying what changed. Finding that one of your own headline numbers was noise is the most useful thing that can happen this week.
Week 28
Resampling seeds is not resampling questions. Running the same 50 questions ten times tells you about decoding variance and nothing about whether your benchmark generalises. Both matter, they are different error bars, and conflating them is the single most common mistake in public eval reports.
"Statistics and experimental design" is a named minimum qualification on Anthropic's Research Engineer, Model Evaluations req. Two weeks here is the cheapest qualification-matching you will do all year, and every later task in this phase reuses it.
Task 05 LLM-as-judge validation Exercise
Label the gold set yourself first
Hand-label at least 100 samples before the judge sees them, writing down the decision rule as you go. Then measure judge–human agreement properly: raw agreement, Cohen's kappa, and per-class breakdown, because a judge that is 90% accurate overall can be useless on the 10% of cases you care about.
Week 29
cohen_kappa_score ↗
Run the bias battery
Test the known failure modes on your own judge: position bias (swap A and B, measure how often the verdict flips), length bias (pad a response without adding content), and self-preference. The MT-Bench paper is where these were characterised and gives you the experimental designs to copy.
Week 29
arXiv 2306.05685 ↗
Rubrics and checklists, not scalar scores
In non-verifiable domains, explicit criteria beat learned reward models — see Rubrics as Rewards (2507.17746) and Checklists Are Better Than Reward Models (2507.18624). HealthBench is the standard testbed: 48,562 physician-written criteria attached to individual conversations. Rewrite one of your judge prompts as a checklist and re-measure agreement.
Week 29
arXiv 2505.08775 ↗
Calibration drift and version pinning
A judge is a model and it changes under you. Pin the exact judge model version in your results, keep the gold set in the repo, and re-run it whenever the judge model, its prompt, or its decode parameters change. Record the agreement number per version so you can tell a real score move from a judge move.
Week 29
Decide what your environment needs
Look at your own tasks and decide honestly whether any of them need subjective grading. If they do, hand-label a hundred samples and measure your judge against them. If they genuinely do not, write the paragraph in your README explaining why programmatic verification is sufficient here — an unexplained absence of judges reads as avoidance.
Week 29
An unvalidated judge is not a metric, it is a vibe. The old plan explicitly avoided judges by only using verifiable tasks. That dodges the most-demanded eval skill in the field: almost everything worth evaluating in 2026 is partly non-verifiable, and someone has to say how much to trust the grader.
Judge accuracy has error bars too. Agreement measured on 100 samples has a confidence interval wide enough to matter. Reuse the Week 35–36 machinery on the judge itself and report the interval, not the point estimate.
Task 06 Eval infrastructure Exercise
A job queue over checkpoints
Build the thing the job req lists first: submit (model, task, sample) jobs to a persistent queue, run them with bounded concurrency, retry transient failures with backoff, and resume cleanly after you kill the process halfway through. Idempotent job keys are the whole design — get them right and everything else is bookkeeping.
Week 30
Caching and dedupe that you can trust

Then test the failure mode deliberately: change a prompt template and confirm the cache misses instead of silently serving last week's answers. Study how Inspect scopes its cache before you invent your own.
Week 30
Inspect caching ↗

Week 30

Week 32
Learn where computer-use numbers hide
Computer-use evals are the worst offenders and the best teacher. Step budget is an undeclared free parameter — the same Claude Sonnet scores 42.9%, 58.1% and 62.9% on OSWorld-Verified at 15, 50 and 100 max steps, and one model scored *worse* with more steps. Labs run their own harness and retroactively restate: an Anthropic post claims 84.3% while the maintainer's verified table tops out at 72.1%, same benchmark name, different harness. Best-of-N gets reported as if it were pass@1 — a headline "72.6%, above the 72.36% human baseline" was ten rollouts plus a judge. Read the flag columns before the score column.
Week 32
Measure what a single number hides
Rerun your chosen tasks several times and report the spread, because the same task and the same model will succeed once and fail on repeat — execution stochasticity, ambiguous task specs and behavioural variability all contribute, and both single-run and Best-of-N figures conceal it. Price it too: OSWorld 2.0 reports roughly $72 per task at the frontier, so a 108-task run is $2,700–7,800, and on GAIA the top agent costs 23× a cheap model for 42 more points. Cost per solved task belongs next to accuracy in your report.
Week 33
Report the discrepancy
Write up your number against the published one with confidence intervals, and separate the explanations: protocol deviation, scaffold difference, model version drift, or genuine irreproducibility. Check the submitted result JSON for protocol-compliance flags — published results have shipped with raised step limits and followed_evaluation_protocol set to "No". File an issue with the maintainers.
Week 33
Harbor harness ↗
Learn which benchmarks are dead and still cited
Part of the writeup is a short survey of what not to trust. WebArena sits within a few points of its human baseline. WebVoyager never had a leaderboard at all. AssistantBench and WebGames are still cited long past usefulness, and the original τ-bench repo is deprecated with README numbers roughly eighteen months stale. In the computer-use cluster specifically: WindowsAgentArena has had no real commit since Nov 2024 and never had a leaderboard, OSUniverse was abandoned in May 2025, and Computer Agent Arena's leaderboard is returning 522s. GAIA is effectively saturated and unauditable — 93.4% against a 92% human baseline, with 3,532 submissions including top-ten entries carrying blank model names and no code or trajectories.
Week 33
arXiv 2307.13854 ↗
Audit your own environment the same way
Turn the audit lens on yourself. What is your undeclared step budget? Could someone inflate a score by varying something you never documented? Week 33
Flagship deliverable 2. Almost nobody applying for evals roles has reproduced someone else's agentic result and reported the gap. It demonstrates the exact skill the work requires — reading a protocol, running it faithfully, and being willing to publish a number that disagrees with a leaderboard.

Week 35
TRL GRPOTrainer ↗
Know where GRPO and DAPO came from
GRPO is introduced in the DeepSeekMath paper: drop the value model, normalise advantage within a sampled group. DAPO then fixes four concrete failures — clip-higher, dynamic sampling, token-level loss, overlong-reward shaping — and the token-level loss is exactly the length-bias fix behind TRL's new default. Read both and you can explain your own config line by line.
Week 35

Week 35

Task 03 PyTorch distributed training Exercise
FSDP2
FSDP2 (`fully_shard`) is the current API and it is not a rename of FSDP1 — it shards on dim-0 into DTensors instead of flattening parameters into a single per-rank buffer, which makes per-parameter state, mixed precision and checkpointing all behave sanely. Wrap a model from Phase 1, run it on two GPUs, and watch memory before and after. Understand what gets all-gathered in forward, what gets reduce-scattered in backward, and why wrapping granularity changes both.

Week 44
github.com/pytorch/torchtitan ↗
Activation checkpointing and gradient accumulation
These are the two levers that trade compute for memory, and you should know the arithmetic for both. Activation checkpointing drops stored activations and recomputes them in backward — roughly 30% more compute for a large memory cut; selective checkpointing keeps the expensive-to-recompute ops. Gradient accumulation buys a larger effective batch at zero memory cost but needs `no_sync` under FSDP or you pay for a reduce on every microbatch. Measure both, do not assume.

NCCL and OOM debugging
Distributed jobs fail in two characteristic ways and you need both playbooks. For hangs: `NCCL_DEBUG=INFO`, `TORCH_NCCL_ASYNC_ERROR_HANDLING`, and the observation that a hang is almost always a collective that one rank did not reach.
